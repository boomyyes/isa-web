# Certificates — How It Works and How to Run It

This is the guide for whoever manages ISA-RAIT workshop certificates. You don't
need to be a developer, but you should be comfortable with Google Sheets, a web
dashboard, and copy-pasting a command into a terminal.

---

## What it does, in plain English

Every student on the roster gets a **UID** and an **access code**, emailed to
them automatically when they're first registered. They go to the **Certificates**
page, sign in with those two things, and get:

- their **digital certificate**, downloadable straight away, and
- a link to request a **printed copy** through the Support page.

If they didn't attend a particular workshop, that one shows as unavailable with
a link to raise a query.

The access code is the only secret. UIDs are sequential and easy to guess, so
everything rests on the code — which is why the system stores it scrambled and
limits how many times it can be guessed.

---

## The four places things live

| Where | What it holds | Who touches it |
|---|---|---|
| **Google Sheet** | Attendance — who came, who's collected a printed copy | You, after every event |
| **Upstash** | The database the website checks people against | Updated by a command you run |
| **Cloudflare R2** | The certificate image files | You upload after every event |
| **The website code** | The list of workshops (titles + dates) | One small edit per event |

The **Sheet is the master copy.** Upstash is a searchable duplicate of it. They
don't sync by themselves — running the import command is what copies the sheet
into the database. Change the sheet and skip the import, and the website will
never know.

---

## What students see

Two checkboxes per workshop decide everything:

| Attended? | Received? | What the student gets |
|---|---|---|
| ❌ | — | "No attendance recorded." Link to Support. No download. |
| ✅ | ❌ | Download button **+** "your first physical copy is **free of cost**" |
| ✅ | ✅ | Download button **+** "additional copies are **chargeable**" |

**Attended?** controls whether they get anything at all.
**Received?** only changes the wording about printed copies — tick it once you've
handed someone a physical certificate, so the site knows the next one is paid.

The digital download always works once Attended? is ticked. It can't be "used up".

## About UIDs and access codes

**The UID** comes from your sheet's UID column. It's the primary key — the one
thing that identifies a student. Two students must never share a UID.

**The access code** looks like `K7P2-9XQM`. It is:

- **Generated by the import**, not typed by you. You never invent these.
- **Issued once.** A student keeps the same code across every future import.
  Re-running the import does *not* reset anyone's code.
- **Impossible to look up.** It's stored scrambled, so nobody — not you, not a
  developer, not someone who steals the database — can read it back. If a student
  loses theirs, you **reissue** a new one; you cannot recover the old one.
- **Forgiving to type.** Not case-sensitive, and the dash is optional.

### Reissuing a lost code

```powershell
npx tsx scripts/import-roster.ts roster.csv --regenerate-uid=42
```

That gives UID 42 a brand-new code, marks them as needing an email again, and
writes it to the handout file. Then run the mailer (step 6 below) and they'll
receive it. Everyone else is untouched.

## The routine: after every workshop

Seven steps. Budget about 25 minutes.

### Step 1 — Tell the website about the workshop

Open `lib/certificates.ts` and find the `WORKSHOPS` list near the top. Add a line
for the new workshop:

```ts
export const WORKSHOPS: WorkshopMeta[] = [
  { id: "wks-1", title: "Industrial PLC Programming", date: "2026-01-24" },
  { id: "wks-2", title: "SCADA & HMI Design",        date: "2026-03-14" },
  { id: "wks-3", title: "Process Instrumentation",   date: "2026-05-17" },
];
```

- **`id`** — keep the `wks-1`, `wks-2`, `wks-3` pattern. This has to match both
  your sheet's column heading and your folder name in R2 (steps 2 and 4).
- **`title`** — what students see on the card. Use the real workshop name.
- **`date`** — always `YYYY-MM-DD`.

Save, then deploy the site as usual.

### Step 2 — Add the columns to the sheet

Add two new columns for the workshop, matching the existing pattern: a `WKS 4`
heading spanning two columns, with `Attended?` and `Received?` underneath. Tick
Attended? for everyone who came.

Make sure every new student has a **UID** and an **Email**. The UID is how they
sign in; the email is the only way to send them their code.

### Step 3 — Make the certificate images

Generate them however you normally do (Canva, Illustrator, a mail-merge). Then
name every file **exactly** after the student's UID:

```
1.png
2.png
```

The UID in the filename must match the **UID** cell character for character.
`01.png` and `1.png` are different files as far as the computer is concerned.

Only make files for people who attended.

### Step 4 — Upload the images

Put them in a folder named after the workshop `id`:

```
wks-4/1.png
wks-4/2.png
wks-4/7.png
```

Go to the **Cloudflare dashboard → R2 → `isa-certificates` → Upload**, and drag
the `wks-4` folder in. Make sure the folder name is preserved — you should end up
with files listed as `wks-4/1.png`, not just `1.png`.

> **Leave the bucket private.** Never turn on public access or the `r2.dev`
> domain. The site hands out temporary two-minute links after checking that the
> person is actually entitled to the file. Making the bucket public would let
> anyone download anyone's certificate.

### Step 5 — Copy the sheet into the database

Export the sheet: **File → Download → Comma Separated Values (.csv)**. Keep both
header rows. Save it into the project folder as `roster.csv`.

Open a terminal in the project folder and do a practice run first — this changes
nothing:

```powershell
npx tsx scripts/import-roster.ts roster.csv --dry-run
```

**Read the output before going further.** Three lines matter:

```
Header resolved — 4 workshop(s), data from row 3.
Plan: 143 to write, 2 to delete (145 currently stored).
      6 new access code(s), 137 carried forward unchanged.
```

The **workshop count** must equal the number of workshops in your `WORKSHOPS`
list. If it's lower, one of your columns wasn't recognised, and **everyone would
be imported as absent for that workshop.** Fix the heading and try again.

The **delete count** must match what you expect. `0 to delete` is normal for a
routine update. A number you can't explain means your export is incomplete —
stop and check the file.

The **new access codes** count should equal the number of students you just
added. If it's unexpectedly large, something is wrong — see the troubleshooting
table.

Also read any lines starting with `!` — they flag duplicate UIDs, rows with no
UID, students with no email address, and unmatched columns.

When it looks right, run it for real:

```powershell
npx tsx scripts/import-roster.ts roster.csv
```

If any new students were registered, this writes **`new-access-codes.csv`**.

### Step 6 — Email the new students their codes

`new-access-codes.csv` is the **only** copy of those codes in readable form.
Preview who would be contacted — this sends nothing:

```powershell
npx tsx scripts/send-passwords.ts
```

When the list looks right, send for real:

```powershell
npx tsx scripts/send-passwords.ts --send
```

**Nobody is ever emailed twice.** Each student is stamped in the database once
their mail goes out, and stamped students are skipped forever after — even if you
re-run this, run it from another computer, or still have an old handout file
lying around. If a send fails halfway, just run it again; it picks up exactly
where it stopped.

Once the mail has gone out, **delete `new-access-codes.csv`.**

### Step 7 — Check it worked

```powershell
npx tsx scripts/check-setup.ts
```

Confirms both services are reachable and tells you how many records are stored.
Then open the Certificates page and sign in as a couple of real students.

## Changing things later

**Any** change to the sheet — a corrected name, a newly ticked box, a student
added or removed — reaches the website the same way: re-export the sheet, re-run
the import. There is no other sync, and nothing happens automatically.

The import handles all cases:

- **Added** a student → record created, **new access code issued**, and they turn
  up in the mailer's queue.
- **Changed** a tick or a name → record updated, **code untouched**.
- **Deleted** a row → record removed from the database too.

Re-running is safe and repeatable. It never duplicates records and never resets
anyone's access code.

The most common use is ticking **Received?** after handing someone a printed
certificate, so the site starts telling them additional copies are chargeable.

## Going live: replacing the practice data

The site currently holds six fake students (Aarav Sharma and friends, UIDs 1–6)
and twelve fake certificates, for testing.

Importing your real roster removes the fake students **automatically** — they're
not in your CSV, so they get deleted. Because that's a large turnover, the safety
net will stop you the first time. This is what `--force` is for:

```powershell
npx tsx scripts/import-roster.ts roster.csv --force
```

The twelve sample images in R2 are *not* touched by the import. Delete them from
the Cloudflare dashboard yourself, so nobody stumbles onto a file stamped
"SAMPLE · NOT A REAL CERTIFICATE".

## Five rules you must not break

**1. Filenames must match UIDs exactly.**
`wks-4/7.png` is found. `wks-4/7 .png`, `wks-4/UID7.png`, and `wks-4/7.PNG` are
not.

**2. One UID per student, never reused.**
The database is organised by UID. If two rows share one, only one of them
survives. Worse, if you ever recycle a departed student's UID for a new person,
the new person inherits the old one's record. The import warns about duplicates;
don't ignore it.

**3. The `UID` and `Name` columns must be called exactly "UID" and "Name".**
Not "Student Name", not "Uid No.". The `Email` column is relaxed — anything
containing "email" works. If UID, Name or Email is missing entirely, the import
stops and tells you, so this fails safely.

**4. The CSV you import is the whole truth.**
Anyone in the database but *not* in the file gets **deleted**. That's what makes
removing a student work — but it also means importing a partial export wipes
everyone who isn't in it. Always export the full sheet, never a filtered view.

There is a safety net: an import that would delete **more than 20%** of the
stored roster stops and refuses:

```
REFUSING TO PROCEED — this would delete 3 of 6 record(s) (50%).
```

Check your export first. If the removal really is intended, re-run with `--force`.

**5. Never run `--regenerate` casually.**
`--regenerate` (no `=`) resets **everyone's** access code, invalidating every code
you've ever sent out and requiring a full re-mail. To help one student who lost
theirs, use `--regenerate-uid=42` instead.

## When something goes wrong

| What you see | What's probably wrong | Fix |
|---|---|---|
| "That UID and access code don't match" for a real student | Wrong code, or they were never imported | Confirm their UID in the sheet; reissue with `--regenerate-uid=` if the code is lost |
| A student never got their email | They had no email address in the sheet, or the send failed | Check the import warnings; add the address, re-import, re-run the mailer |
| "Too many attempts. Try again in a few minutes." | Normal protection — 10 tries per 10 minutes for a given UID | Wait it out |
| Download button appears but the file fails to download | The image isn't in R2, or the filename doesn't match the UID | Check `wks-N/{uid}.png` exists in the bucket, spelled exactly |
| Everyone shows as "Not Attended" for one workshop | The sheet column wasn't recognised during import | Re-run with `--dry-run`, check the "N workshop(s)" number, fix the heading |
| No card at all for a workshop you just ran | It's missing from the `WORKSHOPS` list, or the site hasn't been redeployed | Step 1, then deploy |
| Import reports far more "new access codes" than students you added | The UID column changed, or UIDs were renumbered — the system sees them as brand-new people | Stop. Restore the old UIDs; renumbering forces a full re-mail |
| "REFUSING TO PROCEED — this would delete N of M records" | Partial or filtered export | Re-export the whole sheet; add `--force` only if intended |
| "Certificate lookup is unavailable right now" | The site can't reach the database | Run `check-setup.ts`; if it's the live site, check the environment variables in the hosting dashboard |
| A student you removed can still sign in | You haven't re-run the import since removing them | Re-export and import |

## Useful commands

Run all of these from the project folder.

```powershell
# Check the database and file storage are both working
npx tsx scripts/check-setup.ts

# Practice import — changes nothing, shows you what would happen
npx tsx scripts/import-roster.ts roster.csv --dry-run

# Real import
npx tsx scripts/import-roster.ts roster.csv

# Import when your certificates aren't PNGs
npx tsx scripts/import-roster.ts roster.csv --ext jpg

# Override the "too many deletions" safety net — only when you're sure
npx tsx scripts/import-roster.ts roster.csv --force

# Reissue the access code for one student who lost theirs
npx tsx scripts/import-roster.ts roster.csv --regenerate-uid=42

# Preview the access-code emails — sends NOTHING
npx tsx scripts/send-passwords.ts

# Actually send them
npx tsx scripts/send-passwords.ts --send

# Rebuild the practice/demo data (6 fake students + fake certificates)
npx tsx scripts/make-sample-data.ts

# Run the site locally at http://localhost:3000
npm run dev
```

## Setting up email (one-time)

The mailer sends through any normal SMTP account — put the details in
`.env.local` (see `.env.example` for the full list).

For a Gmail or Google Workspace account:

1. Turn on 2-step verification on the account.
2. Create an **App Password** at *myaccount.google.com → Security → App
   passwords*. Your normal account password will **not** work.
3. Put that app password in `SMTP_PASS`, with `SMTP_HOST=smtp.gmail.com` and
   `SMTP_PORT=587`.
4. Set `MAIL_FROM` to the address students should see, and `SITE_URL` to the live
   site address so the link in the email points to the right place.

Gmail caps sending at a few hundred messages a day, which is ample for a club —
but if you register several hundred students at once, expect to run the mailer
across two days.

## A note on student privacy

The sheet holds real names, emails and UIDs. The system is built to keep that
contained, and it's worth not undoing it:

- **Phone numbers are never uploaded.** The import ignores that column entirely.
- The website only ever shows a **name and attendance** — never an email address
  or college — even to the person signing in.
- **Access codes are stored scrambled**, so even someone who steals the whole
  database cannot sign in as anyone.
- A wrong code and a non-existent UID give **identical** responses, so nobody can
  fish for which UIDs are real.
- Guessing is capped at **10 tries per 10 minutes per UID**, no matter how many
  computers the attempts come from.
- Certificate files are private and only reachable through **two-minute links**
  issued after a successful sign-in.

Practical consequences:

- **Never commit a roster CSV or `new-access-codes.csv` to git.** The project
  ignores `.csv` files automatically — don't work around it.
- **Delete `new-access-codes.csv` once the emails have gone out.** It is the only
  plaintext copy of those codes.
- **Never make the R2 bucket public.**

## Glossary

- **UID** — the number identifying a student, from your sheet. Their username.
- **Access code** — the secret they type alongside it, like `K7P2-9XQM`.
- **Upstash** — the online database holding the roster.
- **Cloudflare R2** — the online storage holding the certificate image files.
- **R2 bucket** — the specific folder-of-folders in R2, named `isa-certificates`.
- **CSV** — a plain-text spreadsheet export. What the import command reads.
- **Import** — the command that copies your sheet into the database.
- **Dry run** — a practice run that shows what would happen without changing anything.
- **Handout file** — `new-access-codes.csv`, the temporary list of newly issued codes.
- **SMTP** — the standard way programs send email; how the mailer talks to Gmail.
- **Deploy** — publishing your code changes to the live website.
- **Environment variables** — the passwords and addresses the site uses to reach
  Upstash, R2 and your mail account. They live in `.env.local` on your machine
  and in the hosting dashboard for the live site. Never committed to git.
